## 规则和出处

三种方法的统一 JSON、字段规范和数字编号规则见 [命理统一资料库 JSON](REPORT_KNOWLEDGE_FORMAT.md)。

正常运行的匹配规则和铁板选择器由统一 JSON 导入。SQLite 把数字 ID 关联到既有来源 ID 和实际命中分句，CLI 的 `explain` 支持两种编号。原始 Claim 和旧种子仍提供出处档案、校订内容和现有算法使用的查表资料。

每条解读包含关键词、正文与主题。匹配先检查术数、排盘口径和时间层，再按 `input` 核对必要事实、备选条件组、明确排除事实、关系及数值区间。报告请求保留结构化盘面事实，关键词供检索索引和排查使用。旧种子沿用原 `required` 与 `mustBeAbsent`。

每条旧规则通过稳定的 ID 关联 `rule_provenance` 中的出处登记。登记包含书名、作者、版本、卷章或段落定位、链接、依据类型、原规则依据和适用限制。部分来源附有备用阅览链接。原典定位支持回查传统含义。原创组合释义由登记的术数规则及主题推导，出处用于追溯该依据，原创解读正文由项目维护。

## 报告取材

`knowledge_entry` 对整条规则和 Claim 提供 `source_json`、`original_text`、`modern_interpretation` 和 `original_kind`。已收录引文保留原字句。旧规则若只登记了整理文字，就保留原规则编写依据，并标记为 `rule_basis`。模型收到的材料也明确标记此类原文的性质。

每个 `claim_branch` 保留分句的 `text`、`modernInterpretation` 和 `interpretationOrigin`，通过 `claim_id` 关联出处。可在 [分句解读](claims/branch-interpretations.json) 按 Claim ID 和完整分句原文维护人工释义（`reviewed`）。原文覆盖整条且已有释义的分句沿用来源释义（`source`）。能用词语转换得到独立白话的分句保留转换结果（`derived`）。其余分句将现代释义留空（`untranslated`），继续保留原文和命中条件。修改源文件后重建 SQLite。构建会校验人工释义仍对应有效分句。

报告 prompt 按实际命中的统一条目提供「原文：」「现代解读：」及该条的「命中条件：」。多组条件分别呈现，校订分句及大运摘录须与实际规则组完整对应。数字 ID、出处、原资料使用边界、整盘和计算明细保存在本地，可通过查询和导出追溯。系统提示词统一说明古籍命例和铁板条文的用法。铁板查号过程和结果留在本地计算及服务响应。

### 报告资料筛选

报告先取得完整匹配，再按命中条件严苛度、信息具体程度、来源可信度依次比较百分制分数。前一项相同才使用后一项。同主题内，原文、解读和适用范围相同的重复证据保留优先级最高的一条。综合、事业、爱情、学业、财富各取前 40 条，题内不足则按实际命中量取用。命中分句、铁板条文和历史命例都计入配额，合计最多 200 条。单独的查表结果和计算资料用于本地核对。报告接口按完整计算结果提供铁板编号及未命中原因。

- 条件严苛度综合实际盘面约束、重叠条件、可选组合与运限。使用 96 份固定的合成排盘统计条目出现频次，结合盘面约束估计未在样本中出现的条目。
- 信息具体程度检查原文和对应现代解读中的事件、涉及人物、阶段和前后关系。同一个特征重复出现只计一次。
- 来源可信度按出处的可追溯性和资料类型设置档次，《三命通会》的原文资料为最高档。此分数用于确定资料优先级。

三项百分制结合样本经验分位和连续刻度，等分使用并列秩的中点。严苛度按每次命中统计分布，具体度和来源按不同条目统计，避免常见资料被重复计权。校准使用覆盖不同年份、时辰、性别和地点的合成样本，无需调用模型。资料或评分规则更新后，可在仓库根目录运行 `node src/features/destiny/server/calibrate-report-ranking.mjs` 重新生成 [校准数据](../report-ranking-calibration.json)。

## JSON 资料源与 SQLite 运行库

命理可查询资料库统一采用「JSON 保留为可审查的资料源，SQLite 作为运行时查询库」。导入或更新 JSON 资料库时必须构建 SQLite、接入实际检索并核对完整性；Schema、版本与其他配置 JSON 不属于必须转换的查询资料库。JSON 继续进入 Git 审查，SQLite 是可重建产物，不作为另一份手工编辑的资料源。

三份 Claim JSON 的原始字段逐条保存在 `claim_entry.claim_json`，保留稳定 ID、出处、原文、解释、未映射和跳过状态。`claim_rule` 对重复条件去重，`claim_required_by_fact` 索引用实际已确认的事实筛选所有必要条件成立的候选；`claim_alternative` 与 `claim_branch` 保留备选组、分句顺序和大运锚点。候选随后继续通过原有条件匹配器核对排除、备选组、关系、数值范围及时间层。不是仅把整份 JSON 放进一个 SQLite 单元后继续全量扫描。

唯一运行文件为本目录下 `.local/interpretations/destiny-knowledge.sqlite`，新旧部分在同一构建事务中更新，跨来源 ID 冲突会中止并回滚。历史的 `dual-layer.sqlite` 与 `natal-claims.sqlite` 已不再作为运行查询入口，旧产物保留供追溯。统一库只包含生成资料，不混入账户或用户归档；`.local/` 已被 Git 忽略。换电脑后无需提交或手工复制二进制数据库，运行 `build` 或首次查询即可重建。使用项目现有 Node 22.13+ 的 [内置 `node:sqlite`](https://nodejs.org/download/release/v22.13.0/docs/api/sqlite.html)，不增加 npm 依赖或系统数据库服务。

运行库存在且源文件及编译版本未变化时，仅检查文件版本并查询 SQLite，不重新读取或解析 Claim JSON 内容。JSON 更新时自动检查内容摘要并重建；只有 LF/CRLF 等换行变化时复用原有编译结果。匹配代码或表结构变化后须重启命理服务，新进程将检查版本并重建；检测到运行中的代码已变化会提示重启，避免用旧进程的函数标记新版本。构建使用事务，导入失败回滚保留旧库并报告错误，不悄悄以旧资料回答新请求。

本次合库验收：命理模块全量 101 项测试、类型检查和模块边界检查通过。旧库全部正文、条件和出处与合并前 SQLite 逐字段一致；新版 18,846 条原始记录和全部完整、分句条件组逐条核对一致。专项验证了同一文件同时命中新旧资料、跨来源 ID 冲突时整体回滚，以及无需读取 JSON 内容的就绪查询、自动更新、表版本重建、换行兼容和失败回滚。测试使用隔离样例与替身模型，不消耗模型调用额度。
