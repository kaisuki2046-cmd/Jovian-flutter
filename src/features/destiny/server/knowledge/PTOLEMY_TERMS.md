## 数据与实际调用链

`ptolemy-terms.mjs` 只在构建时转换原始资料，检查原文行、方案、昼夜、连续度数、界主、全座覆盖及重复／缺失。160 条标记为 `calculationReference`，角色为 `term_ruler_table`；不会把表格伪装成无条件的人格或事件规则。

统一 `destiny-knowledge.sqlite` 升级到 schema 4，新增 `ptolemy_term_cell` 与按星座、区间查询的索引。新计算表与旧规则、莉莉计算表仍在同一文件、同一次构建事务内。源资料或编译器变化时重建；失败保留之前的有效文件和数据，不写入半张表。没有创建第二套长期并行回答的运行库。

实际路径：

1. `catalogForDirectory(directory).ptolemyTermReferences(facts)` 在单个 SQLite 读事务中查实际星体位置，返回界主、区间、方案及所据源记录。
2. `createReportLookup` 对本命西占查询调用这个接口，将结果作为综合主题的 `calculationReferences`。
3. `buildReportMaterials` 按七曜合并行，以中文列出独立方案的表值和出处，明确不独立推出性格或事件。
4. `generateReport` 使用这些中文材料，传给模型的原有 `references` 结构不增加内部计算对象。HTTP 返回和归档契约不变。

运行查询不扫描 JSON 数组，不依赖请求方上传已算出的界主，也没有把当用星／目标星座的缺口替换成一条对所有人的断语。

## 位置、昼夜与未知

被查询对象为实际提供经度的传统七曜；界主取表内五颗行星。只有一份一致且处于 `[0,360)` 的黄经才参与。黄道须明确为热带黄道；已声明星座与黄经矛盾、经度矛盾、非有限数或缺失经度均不补造。

迦勒底表在已知昼夜时读相应表。昼夜未定时分别查两表，只在界主一致时返回共识，并保留两个出处；不一致时省略该方案。矛盾的昼夜信息不作共识证据。埃及和古抄本两张不分昼夜的表仍可独立查询。未知出生时间已被请求解析器剔除的黄经不会重新补回。

这里只接通三套印表查询。古抄本双重资格、由一般原则重构界长、寿限主宰、疾病或心性因果等条件并未因此实现；这些资料仍按各自缺口保留。

## 验证与统计

独立表格对照覆盖三套方案、两种昼夜及全部360个整数度，共 2,160 次查询。另覆盖精确端点、359.999…、跨座、未知昼夜一致／分歧、相互矛盾的星座与黄经、缺失坐标、源表损坏、额外未支持要求及版本迁移。

218 张原生排盘产生 109 份合成样例，覆盖全部 240 个单元；每个单元都经过实际星体位置、SQLite 源记录、报告查询与中文材料验证，见 [排盘证据](claims/integration-batch-19-witnesses.json)。模型调用验证使用替身，没有请求真实提供商。

源资料、SQLite 和报告专项 18 项通过，最终命理全量回归194项全部通过，类型和模块边界通过；详见 [接入进度](INTEGRATION_PROGRESS.md)。SQLite 测试同时证明运行时不重新读取 JSON、schema 3 可在原文件升级，以及错误更新会回滚到此前完整数据。

全库计算参考源由144条增至304条，计算单元由160增至400。个人整条／分句索引数保持不变：查表结果与个人断语是不同统计维度，不能把这160条当成新增160条个人预测。其他缺口继续列在 [待接入清单](claims/pending-conditions.csv)。

本批没有公共 UI、账户、其他板块、路由、启动配置或依赖改动；未提交、合入 YA 或推送前，不代表其他工作树已获得这些代码。
